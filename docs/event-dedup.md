# 重置事件通知规则

目标：同一次重置通常只发送一条预告和一条完成；明确时间调整、适用范围更正、撤回单独通知。事件合并不能放宽原有完成证据检查。

首个来源被检测到后立即走正常投递，不等待第二来源。两路在同一轮均出现时按原始发布时间优先；后到来源只补充关联证据，等价阶段不再通知。不同的来源发布时间本身不是计划时间变化。

## 身份与版本

- 共同 X 链接、相容时间范围内的 Day 编号、或同一明确计划时刻构成关联依据；`regular` 与 `banked` 分开。
- 网站回复与 Telegram 主帖可以通过相同明确北京时间关联；发布时间只用于相对日期和合理窗口，不以“同一天”强行合并。
- 缺乏可靠关联或有多个冲突候选时保留独立事件，避免吞掉另一场重置。
- 原始队列继续保留；新增每个目标独立的事件别名和成功记录。观察、入队和发送失败不等于成功。
- 发送前再次查询事件成功记录，覆盖同一批候选里出现多条等价消息的情况。
- 计划时间缺失不能覆盖已知时间；晚到的旧计划不会反复回滚新计划。完成后不补发过时预告。
- 不直接监测个人账号到账，不保证上游始终正确。Webhook 响应丢失后仍存在重复投递窗口。

## 迁移与上线

数据库只新增表或字段。已有成功版本可以建立事件基线，失败版本、ignored 或仅 deduped 记录不能制造新的成功事实；现有游标、重试、配置和状态库保留。上线前 SQLite 一致性备份；回退恢复上一个代码版本，新增表留在原库。无需补发已有预告或测试群消息。

核心验收是今天 Day 23 的两个不同 X ID：网站 10:43 的回复预告和 Telegram 12:13 的主帖转发均指向北京时间 15:00，合并后只发送一条预告；后续明确完成单独发送一次。时间更正和重试另有回归测试。
