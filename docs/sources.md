## 行为

通过环境变量 `CODEX_RESETS_ENABLED=true` 开启，默认关闭。沿用现有每轮等待 60 秒的频率，所有通知目标共用一次网站抓取；网站请求不携带 Telegram relay 或机器人凭据，不继承环境代理，不跟随重定向。

- `scheduled_reset` 始终是重置预告；到达 `scheduled_for` 不自动升级成完成。
- `latest_reset` 只是网站分类，不能单独证明完成。原始正文必须在同一子句明确说明额度重置已完成，且没有否定、条件或疑问，才标为“网站称已完成”；移除 URL 后再判定。只有 `has landed`、`Done` 或链接的记录会保留为未确认并禁止发送，不影响同轮的预告。`observed` 也遵守相同规则，不声称个人账号已到账。
- `active_watch` 是 AI 预测，完全不推送。
- 保留 `regular`/`banked` 的区别，展示公告/观测时间和本次发现时间。
- 首次成功抓取只建立网站基线；不补发已有事件。只有后续新事件或有效内容变化才入队。
- 来源失败相互隔离，失败来源会使 readiness 异常，但主循环继续处理另一来源；已有队列继续重试。
- 网站用独立队列表，与原 Telegram 队列共用每个通知目标自己的 SQLite；重启保留状态，失败最多 8 次，退避 30 秒至 15 分钟，超过 48 小时不发送。
- 同一 X 帖、重置类型及阶段的首次跨来源通知只发送一次。仅在发送成功后记录跨来源凭据；失败版本和旧版本的成功不能冒充当前版本成功。后续实质编辑仍提醒，预告转完成仍提醒。
- 无共同 X 链接的观测事件不做模糊归并，可能收到两条不同来源提醒；避免把不同事件错误合并。

此接口是当前状态快照，不是完整事件流。长时间离线期间出现的中间事件可能缺失；Telegram 原有历史检查仍保留。API 的公告/观测时间不是网站收录时间；`meta.generated_at` 也不是首次发现时间。

2026-10-28 发现网站一度将 `https://t.co/Fgy0dBAHsJ has landed` 归入完成记录，随后 API 移除了该记录并恢复当天重置预告。旧适配器盲信分类导致误报；短链实际指向与额度无关的网站。修复后保存未截断的 `source_text` 并在投递前复验。旧版缺少完整证据的完成待发/失败记录会隔离保留；已发送记录保留审计，明确无效的完成只撤销本来源对应的去重凭据。预告、其他来源和其他事件状态不清空。

这一保守策略可能跳过需要结合上文才能理解的简短完成回复；证据不足时不发送完成通知。第三方即使正文明确也可能出错，个人到账仍以账号实际额度为准。接口中记录消失本身不触发群内更正，避免把普通的“最新记录被替换”误判成撤回。

## 验证与上线

`--dry-run` 在启用补充源后会同时校验两路来源，仍不发消息、不改状态；输出包含 `codex_resets_ok`。评估采集不向群发送消息；任何历史补发都需明确指定事件，避免重放整个来源历史。

上线前备份 SQLite，再部署包含 `codex_resets.py` 的代码并显式开启环境变量。数据库变更只新增 `source_receipts`、`source_meta`、`website_events` 表及 Telegram `source_update` 字段，不清空旧游标。回退可先关闭环境变量；跨来源的成功记录应保留，避免重新发送已通知的事件。
