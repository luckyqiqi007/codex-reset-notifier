# 架构与故障行为

应用由两个标准库模块组成：`configuration.py` 读取并校验配置，`notifier.py` 负责采集、持久化和投递。配置从运行时文件或环境变量注入，不参与镜像构建。

## 数据流

1. 请求固定频道公共页面，解析消息编号、正文、原帖时间和 HTTPS 来源链接。
2. 初次观察只保存基线。以后结合游标与最近 48 小时窗口检查新帖及编辑，每轮最多 10 页。
3. 消息内容摘要变化后，符合条件的记录进入 SQLite pending 队列；已通知帖的更正不要求继续含有“重置”等关键词。
4. 企业微信返回整数 `errcode=0` 才标记成功。HTTP 200 本身不等于投递成功。
5. 抓取和发送分别记录健康状态。失败原因只记录固定错误码或异常类型，避免把带密钥的 URL 放进日志。

## 状态与一致性

SQLite 使用 WAL，记录频道、游标、内容摘要、消息载荷、投递次数与状态。数据库绑定一个频道，换频道需使用独立状态目录。单副本与 Recreate 更新用于避免多个进程同时投递；不支持多实例高可用。

`--dry-run` 只读来源，不创建数据库；`--check-config` 完全离线；`--send-test` 显式发送一条标为测试的消息，不修改频道游标。常驻模式关闭发送时仍更新基线，开启后不补发关闭期间已经观察到的消息。

外部 Webhook 没有幂等键，不能保证严格 exactly-once。若成功响应在网络中丢失，重试可能重复。超过 48 小时的失败消息会过期，持续失败达 8 次则保留为 dead，在窗口到期前令 readiness 失败。

## 观测与维护

- stdout 日志：启动、抓取成功、投递成功、抓取失败、投递失败。
- `state_dir/health.json`：最近 heartbeat/source_success、发送开关及 sent/pending/dead/ignored/expired 数量。
- liveness：主循环 heartbeat 新鲜度；readiness：来源新鲜度及投递错误。
- 监控建议：连续抓取失败、dead/pending 增长、磁盘空间、容器重启、PVC 可用性。具体阈值按使用场景设置。
- 备份 SQLite 时使用 SQLite backup 接口或先停进程，不能只复制正在写入的主 `.db` 而遗漏 WAL。

本项目仅转发第三方来源信息，不接触个人 Codex 账户，也不验证账号到账。
